# src/pi

Pi integration. Cross-cutting contracts live in the root `AGENTS.md`; this file maps the modules and holds constraints specific to them.

## Registration

`src/index.ts` loads the config once and passes it explicitly to each tool factory, which keeps that snapshot for its lifetime. When `enabled` is false it registers nothing. Otherwise it registers tools from their `make*Override` / `makeReplaceTool` factories through one helper that appends `NEXT_GUIDELINE` from `report-schema.ts` (Pi prints the shared guideline once), and calls `registerForgetTool` only when `forget` is enabled. When `actionFusion` is on, the three mutation tools also receive the Action Fusion executor and are wrapped with `withMutationStatus`; `withThenRunDescription` appends the one then_run selection sentence as `withThenRunSchema` adds the field, and the field's `command` description carries the Windows path note only when `process.platform` is `win32`.

## Argument funnel

- Tool files (`read-tool.ts`, `grep-tool.ts`, `edit-tool.ts`, `replace-tool.ts`, `write-tool.ts`) define TypeBox schemas and each mutation tool's description names its alternative (edit ↔ replace ↔ write). Each tool's `prepareArguments` comes from `argument-validation.ts`, then Pi validates against the schema again, and only then calls `execute`. Caller arguments are never rewritten. Each tool supplies only the semantic checks the schema cannot express or name precisely: edit rejects empty bodies, body lines that cannot be written as UTF-8, line numbers beyond the safe-integer range, and anchors of another hash length; replace rejects unwritable replacement text and compiles regex rules; write rejects unwritable content. File-dependent checks stay in execution. Shared integer rules live in `schema.ts`.
- `argument-validation.ts` owns every tool's `prepareArguments` hook, issue collection, bounded diagnostic output, and the Pi schema validation adapter. Tools report semantic field issues through its callback and do not throw during collection. Successful schema conversion informs those checks without changing caller arguments. Observe prepared failures without reimplementing coercion or optional-null rules.
- `argument-diagnostics.ts` owns failure-only schema projection and structured aggregation. Top-level tool fields have independent schemas; failure diagnosis derives field schemas with TypeBox and keeps Pi's coercion and per-field error limits. Derive branches, choices, and the explanations of missing, forbidden, and pattern-mismatched fields from the declared schema: when a schema reason does not say how to correct the value, a missing or pattern-mismatched field's `fix` is its description (each choice's value and description), and a forbidden field's `fix` lists the selected shape's accepted fields after the meaning of the operation that selected it. Suppress only inapplicable or already explained issues, and retain independent fields with bounded native diagnostics.
- `argument-error.ts` owns the JSON argument-error envelope and its byte budget: retain exact field paths, omit whole issues or the argument copy with explicit markers, and never truncate serialized JSON. Preparation failures use the same envelope.

## Mutations

- `mutation-runner.ts` owns the call sequence shared by `edit`/`replace`/`write` after Pi has validated the arguments: separating `then_run`, path resolution, `withFileMutationQueue`, and the hand-off to Action Fusion or plain finalization. Each tool's `run` returns a typed `MutationOutcome` (commit facts, details, outcome facts), and only `finalizeMutation` turns it into a result; nothing downstream reads publication or revisions back from result details. `runTextMutation` owns the read-modify-write for `edit`/`replace`, so each tool supplies only a `TextChange` (new text, outcome facts).
- `file-read.ts` provides guarded stream and whole-file reads; byte revision checks stay in the search and commit owners.
- `file-commit.ts` is the only publication path: SHA-256 revisions (`byteRevision`/`fileRevision`), no-op detection, a temp file in a sibling dir, then `link` (create) or `rename` (overwrite). It handles symlinks and hard links, preserves file modes, and syncs the directory on POSIX. It throws `FileMutationError` with a `stage` and a publication status; a failed step is the `message`, its underlying error the `cause`. `edit`/`replace` pass the revision of the bytes they read as `expectedRevision`. It also owns freshness: `commitFreshness` from the commit result and `observeFreshness` for Fusion's later observations.
- `mutation-result.ts` builds diff details and defines `MutationOutcome` and `finalizeMutation`, which returns one mutation report from commit, tool, freshness, and command facts. `failure-context.ts` turns anchor failures into a `HashlineError` with bounded facts (`failures`, `matched`, `candidateNeighborhoods`); `anchor-format.ts` owns the `LINE#HASH` syntax, its schema pattern, and row parsing.

## grep

- Split into `grep-tool` (schema and execution order), `grep-scope` (paths and glob admission), `grep-search` (candidate listing, worker pool, per-file revisions), `grep-output` (payload rows, file-header format and its parser, and grep's report facts), and `grep-render` (TUI rows). Grep reads each candidate file once through `text-stream.ts` (via `scanTextFile`) for NUL, UTF-8 validity, its revision, and the lossy LF view it matches. README defines resource limits and physical-line reporting; document file and worker budgets there.
- Without `multiline`, `rg-regex.ts` translates each pattern into rg patterns that list every line the query matches: keep a construct only where both engines give it the same meaning over the original line bytes (CRLF, malformed UTF-8, surrogate halves included), and otherwise widen it; never narrow. Bound fixed-width assertion constraints, finite capture bindings, string expansion, and emitted patterns. Preserve every alternative, including branches outside an impossible capture. A multiline query, unsupported or oversized translation, or pattern rg rejects before reporting a file uses the file prefilter.
- `rg-process.ts` is the ripgrep process layer: spawning, bounded reading, the line listing (`runRgLines` reads rg's per-file line numbers; workers re-check only those lines through `searchLines`), and the candidate-file arguments (`--files-with-matches` over the necessary literals, or `--files` when none is necessary). `runCandidatePaths` owns clause intersection and bounded retained paths; overflowing retention falls back to one necessary clause. Scope flags are produced only by `scopeArgs` and never parsed back.
- Keep grep matching in the bounded, cancellable worker pool of `grep-search.ts`: a lazily started pool, each worker sending `core/search.ts` whole lines in bounded requests, or the whole file for a multiline query.
- `grep-scope.ts` classifies scope errors: only `ENOENT` means `PATH_NOT_FOUND`; preserve other filesystem errors.

## Regex workers

`regex-worker.ts` owns serialized requests, timeout, cancellation, and cleanup for grep and replace workers. Their `.mjs` bootstraps load TypeScript through `jiti`, because workers do not inherit Pi's loader; workers never import the Pi runtime and trust inputs validated at tool entry. `replace-regex.ts` sends regex batches to `core/replace.ts`; literal-only batches remain in-process. `config.ts` owns both timeout settings. The host validates exactly-one-result replies with `regex-worker-contract.ts`, using result schemas and code-specific facts from `report-schema.ts`; `replace-worker-contract.ts` owns replacement request/result shapes. Bound worker failures only in the receiving tool.

## Reports and rendering

- `report-schema.ts` is the single definition of the result protocol: every report field in output order (each with one owning layer), every error code with its facts schema and recovery (`next.default` plus named alternatives), and the success recovery order (`OUTCOME_NEXT`). Types derive from it. Its closed wire schemas validate text-only reports, enforce legal tool names, and require code-specific facts.
- `report.ts` builds reports and owns their one model-facing serialization (`renderReport`: one JSON object, fields in schema order) and serializes only report facts. `reportResult` appends a success report after the tool's payload; every tool's `execute` runs inside `runTool`, which classifies a failure (`describeFailure`, structured `cause`, `next` from code and publication) and returns it as an `isError` result whose `details.report` the TUI renders.
- `render.ts` (`reportLines`) is the one TUI renderer of a report and holds the shared tool renderers. Failure rendering uses `details.report`; Pi raises argument errors before execution, so text-only argument rejections and forget tags decode from the final content block with `decodeReport`. Invalid text-only reports remain raw.
- `report-cause.ts` transports structured causes without Pi runtime imports, preserving cause chains and aggregate branches with cycle and repeated-reference protection; reports and worker replies share it. Native failures state the original diagnostic and errno once in `message`, retaining only an actual underlying `Error.cause`.
- `error-text.ts` holds the Pi-layer error forms (cancellation, file changed during read or search). `diagnostic-buffer.ts` bounds stderr and search diagnostics.

## Budgets and config

- `budgets.ts` derives model-facing byte budgets from the selected model's declared `contextWindow`, with bounded defaults for unknown limits. `model-budgets.ts` caches one immutable snapshot per extension, calculated lazily and replaced when selection or capacity changes; preparation shares its provider, and each execution captures the snapshot before its asynchronous work. Model-derived content budgets share the `MAX_CONTENT_KIB` ceiling that the explicit `read.maxKiB` range also uses.
- `config.ts` defines the `hashlineEdit` settings as one TypeBox schema: top-level `enabled`, `actionFusion`, `forget`, `hashLen`, `shiftRadius` control shared behavior; the `read`, `grep`, and `replace` groups hold tool-specific settings. Missing or invalid optional `read.maxKiB` selects automatic model sizing.

## Action Fusion

`action-fusion.ts` implements `then_run`. After a successful mutation it checks freshness against `publishedRevision`, then runs the command through the session Bash tool. Its own per-file queue wraps mutation and command around Pi's `withFileMutationQueue`; the module header explains the nesting. Fusion states only the command (`then_run` status and output, `terminate`); freshness and publication come from the mutation report. Fusion progress derives from `ACTION_FUSION_PROGRESS_SCHEMA`; `fusion-card.ts` validates saved command cards against its closed projection before restoring them. It renders the separate mutation and command TUI cards (`withMutationStatus`, `registerFusionCards`) and derives a not-run reason from the same facts.

## forget

`forget-tool.ts` implements `forget`, disabled by default through the `forget` setting. When enabled, read and grep tag large results with `withResultTag`, which adds the forget-owned `resultId` fact to their report; a `context` handler records the tagged results of the previous response, `forget` forgets the named ones among them and reports the rest in `notForgettable` (failing with `NOT_FORGETTABLE` only when none qualifies), since no later response can forget them, and its `turn_end` handler uses Pi's `context_edit` to replace each result's entire content with a forgotten receipt. It does not parse or classify the content; the original tool call and facts saved in `note` remain. Older results are never edited, so the next request changes only from the earliest replaced result on: later results of that batch, the response that asked, and its tool results. Tagged results also carry a display-only `forgetReceipt` in details (`readReceipt`/`grepReceipt`), which `forget` copies into its own details for the TUI card; nothing of it reaches the model.
