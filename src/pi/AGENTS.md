# src/pi

Pi integration. Cross-cutting contracts live in the root `AGENTS.md`; this file maps the modules and holds constraints specific to them.

## Registration

`workspace.ts` queries the Pi loader's default `pi.exec()` cwd: Windows uses `workspace-cwd.js` through Windows Script Host with a PowerShell fallback, and macOS and Linux use `/bin/pwd`. `src/index.ts` loads config once for that workspace and registers nothing when `enabled` is false. Tools and entry renderers register in the factory because Pi can rebuild history before `session_start` on reload. Each tool factory receives one environment: `ToolEnvironment` (`cwd`, `config`, and the `budgets` provider; `config.ts`) for `read` and `grep`, and `MutationToolEnvironment` (the same plus `schedule`, the mutation scheduler chosen once from `config.actionFusion`; `mutation-runner.ts`) for `write`, `edit`, and `replace`. Tools register in the order write, edit, replace, read, grep. The Action Fusion cards register even when Action Fusion is off, so saved then_run cards render. One helper appends `NEXT_GUIDELINE` from `report-schema.ts` to every tool's `promptGuidelines` (Pi prints the shared guideline once). The `then_run` field and `ACTION_FUSION_GUIDELINES` exist only when `config.actionFusion` is true; that guideline is the one place the model is told when to use then_run.

## Argument funnel

- Call order: a tool's `prepareArguments` (from `argument-validation.ts`), then Pi's schema validation and mutable `tool_call` hooks, then an owned snapshot at `execute`. The tool checks that snapshot against the same schema and semantic rules without coercing hook edits. Caller arguments are never rewritten. File-dependent checks stay in execution.
- Tool files define TypeBox schemas, and each mutation tool's description names its alternative (edit ↔ replace ↔ write). A tool supplies only the semantic checks its schema cannot express or name precisely: edit's per-action fields and ranges, text that cannot be written as UTF-8, and regex compilation through `checkRegexArguments` in `argument-validation.ts`, which reports flags V8 rejects and compiles regex-mode patterns under the flags each tool uses. Shared integer rules live in `schema.ts`.
- Every tool declares `STRICT_SAMPLING` from `schema.ts` (mutation tools through `mutationToolBase`) and keeps its parameters convertible by Pi's strict converter: no object or array unions, so grep's multi-valued fields are arrays only and each edit item is one flat object whose `EDIT_OPS` table, not the schema, fixes the fields per action.
- Some providers emit keys in declaration order and others alphabetically, so the `edit` and `replace` keys are declared in alphabetical order (`path`, `steps`, `then_run`; `action`, `anchor`, `end`, `lines`; `path`, `replacements`, `then_run`): both orders stream the file and each operation's action and range before the payload.
- `argument-validation.ts` owns every tool's `prepareArguments` hook, issue collection, bounded diagnostic output, and the Pi schema validation adapter. It coerces one copy with Pi's schema engine, formats, and unresolved-reference policy. The schema check, semantic checks, and failure diagnostics use that copy. Tools report semantic field issues through the callback without throwing during collection. The boundary parses each local path spelling, reporting Node's reason for an invalid file URL. Execution receives the original spelling and the absolute path resolved against the tool's cwd. The edit check parses anchors during semantic validation and builds core steps only for the accepted execution snapshot. The boundary checks array shape on structured-clone snapshots of the arguments (enumerable own string-keyed properties of ordinary objects and arrays) before preparation coercion and before post-hook semantic checks. Arrays in either snapshot must have no holes or named properties. Both checks follow the item schema for a singleton at its original path, where Pi wraps it; the schema check still rejects a singleton a hook leaves at an array field. Execution uses the checked post-hook snapshot. Preparation hands Pi the same raw snapshot for coercion and validation. Pi's coercion is copy-on-write. Do not reimplement coercion or optional-null rules.
- `argument-diagnostics.ts` owns failure-only schema projection and structured aggregation. Top-level tool fields have independent schemas; failure diagnosis derives field schemas with TypeBox and keeps Pi's coercion and per-field error limits. Derive choices and the explanations of missing, undeclared, pattern-mismatched, and out-of-choice fields from the declared schema: when a schema reason does not say how to correct the value, the `fix` of a missing field, a pattern mismatch, or a value outside the field's choices is the field's description (each choice's value and description), and an undeclared field's `fix` lists its object's accepted fields. A declared field is applicable even when absent, so a tool check may require it. An issue on a whole object leaves its fields' diagnostics in place. Suppress only inapplicable or already explained issues, and retain independent fields with bounded native diagnostics.
- `argument-error.ts` owns the JSON argument-error envelope and its byte budget: retain exact field paths, omit whole issues with explicit counts, and never truncate serialized JSON or repeat the call's arguments. Preparation failures use the same envelope.

## Mutations

- `mutation-runner.ts` owns what the mutation tools share: their definition (`mutationToolBase`) and the call sequence after validation (separating `then_run`, `withFileMutationQueue`, the hand-off to the scheduler, and finalization). The `actionFusion` setting chooses the scheduler once at registration: `runAlone`, or Action Fusion's, which every mutation tool shares; the same setting adds `then_run` to the schema with its guideline and card. A tool supplies its schema, text, semantic checks, `run`, and renderers. The runner's per-call `publish` records the commit result before handing it to the tool. The publish call also records a `FileMutationError`'s publication if the commit throws. After a commit returns, every failure keeps its publication, including a no-op. `run` returns a tool-indexed `MutationOutcome`, the scheduler returns a `SettledMutation` (`alone`, or `fused` with its command facts), and one `finalizeMutation` call turns it into a result; nothing downstream reads publication or revisions back from result details. `runTextMutation` owns the read-modify-write for `edit`/`replace`, which supply only a `TextChange`.
- `file-read.ts` owns guarded byte acquisition and the mutation snapshot. It checks the opened handle and current path and hashes each chunk once. Mutation reads require the initial size of a regular file and reject premature EOF. Revision-only checks reuse one chunk buffer and retain only the digest. Editable snapshots retain filled chunks and join them for decoding when there is more than one. Text scans use Node's read-ahead to EOF, including virtual files that report zero size. `read` hands supported images to Pi's native read through Pi's image-detection API, delegates files containing NUL to it, and rejects all other invalid UTF-8; Pi owns those delegated reads. Delegated read uses Pi’s image-resize setting captured when the session starts, or on the first delegated read if the SDK reload skips `session_start`. Pi gives extensions no copy of the value it passed to its native read, so an SDK host that changes the setting after building the runtime and before the extension first reads it gets the new value in delegated reads and the old one in Pi's native read. The native MIME probe checks the target again at delegation because it can change after the dispatch probe.
- `file-revision.ts` defines a revision once as the SHA-256 hex of the exact bytes. `text-stream.ts` handles streaming text and returns the revision from `file-read.ts`.
- `file-commit.ts` publishes: no-op detection, a temp file in a sibling directory, then `link` (create) or `rename` (overwrite). It stages overwrites beside the resolved target and rechecks the requested path and target admission before renaming. It preserves existing file modes (a new file follows the umask) and syncs the directory on POSIX. A failure with a publication status to state throws `FileMutationError`; every other failure stays a plain `HashlineError`, reported as `NOT_PUBLISHED`. A commit intent is `create`, `overwrite`, or `update` (read-modify-write, the only one with a `baseRevision`); `planPublication` inspects the target once and returns the publish plan the rest of the commit follows, and the result states the freshness observed right after publication. It also owns freshness: the commit result's own, and `observeFreshness` for Fusion's later observations; only unknown freshness carries an observation error.
- `mutation-result.ts` owns final success/failure details and progress details. It builds diffs and finalizes each mutation from its tagged tool facts, commit, freshness, and command facts. On failure after a returned commit, `describeMutationFailure` wraps the original cause as `POST_PROCESS_FAILED`. It passes the recorded publication, known command status and first display error to `describeFailure`, which keeps those facts even when inspecting a thrown value fails. `failure-context.ts` turns anchor failures into a `HashlineError` with `failures` and bounded `candidateNeighborhoods`. The report layer bounds the `failures` list. `anchor-format.ts` owns the `LINE#HASH` syntax, its schema pattern, and row parsing.
- `mutation-diff.ts` keeps the Pi diff row format. Whole rows proven by copied spans delimit changed ranges. A BOM common to both snapshots stays with the file, so the first row's copied body can establish its identity independently of the BOM. When adding or removing a neighboring row changes the last line's terminator, a copied full body identifies the surviving row. jsdiff's `diffArrays` aligns each range under the line edit-distance budget. If the search exceeds the budget or leaves a proven row unmatched, the card preserves the proven match and shows the remaining original and replacement rows as blocks. Saved details carry the diff text.

## grep

- Skip NUL files. Invalid UTF-8 output stays as plain preview rows, and matching uses the lossy preview text. Content mode re-reads each matched file and keeps it only when that read has the revision it was matched on; files and count modes report the searched snapshot without re-reading.
- Validate patterns with V8 at tool entry and resolve smart case once into `GrepQuery.ignoreCase`. Native `RegExp` in `core/search.ts` decides every match on the LF view; rg only lists candidates and never decides a match. Candidate derivation may widen but never narrow.
- Split into `grep-tool` (schema and execution order), `grep-scope` (paths and glob admission), `grep-candidates` (candidate strategy, fallback, whole-scope scan budget, and the empty-scope guard), `grep-search` (queue backpressure, worker pool, per-file matches with their revisions), `grep-reread` (content mode's bounded second read of each matched file and its revision check), `grep-output` (payload rows, the gap row between a file's groups of context rows, file-header format and its parser, and every grep report fact, including empty and incomplete searches), and `grep-render` (TUI rows). Each candidate file is scanned once through `text-stream.ts` for NUL, UTF-8 validity, its revision, and its decoded text (lossy for invalid UTF-8). Each stage returns ordered `SearchWarning` records (`{ path?, reason }`) in its result rather than composing sentences; `grep-tool` joins stages in order, and only `grep-output` formats diagnostics with cwd-relative paths, de-duplicates them, and applies the field budget. The README documents grep's resource limits.
- Without `multiline`, `rg-regex.ts` translates each pattern into rg patterns that list every line the query matches: keep a construct only where both engines give it the same meaning over the original line bytes (CRLF, malformed UTF-8, surrogate halves included), and otherwise widen it; never narrow. Bound emitted patterns. Preserve every alternative. In a backreference's repeated text, membership keeps each node's original scoped case flags, and the reference's case widening is applied afterward through the existing byte translator (`scalarRanges`, `backreference`). A multiline query, unsupported or oversized translation, or pattern rg rejects before reporting a file uses the file prefilter.
- `rg-process.ts` is the ripgrep process layer: spawning, bounded reading, and parsing rg's output protocols (`runRgPaths` reads NUL-delimited paths; `runRgLines` reads the per-file line numbers of `LINE_LISTING_ARGS`). It knows no candidate strategy. Every rg run takes the tool workspace as its working directory, because rg resolves caller globs against it, and a missing workspace fails as it does for Pi's bash. Pi's built-in grep inherits the host's directory, so its globs resolve against the process directory in an embedded session; this difference from Pi is deliberate. Completed-run diagnostics leave this layer as reason-only warning data; path formatting belongs to `grep-output`. Scope flags are produced only in `grep-scope.ts` and never parsed back.
- `grep-candidates.ts` decides which rg runs to make: line candidates through `rg-regex.ts`, then file candidates through `--files-with-matches` over necessary literals. A stage falls back only when its arguments exceed the command line, or when it exits with code 2 before listing any file and `rgRejectsPatterns` confirms rg rejects its patterns; a search that only hit unreadable paths stands. When the file filter is unavailable or falls back, `--files` lists every file in scope. Byte-level pattern flags are defined once there.
- Keep grep matching in the bounded, cancellable worker pool of `grep-search.ts`: a lazily started pool, with each worker passing original decoded text to `core/search.ts` for CRLF normalization and matching. A request carries selected or contiguous whole lines with their original terminators, or the whole file for a multiline query. The host maps selected rows back to their file line numbers. Commit file results, warnings, and fatal failures in listing order; retire a worker after a fatal file result, and replace it if a later NUL made its failure irrelevant. Propagate cancellation without waiting for earlier files.
- `grep-scope.ts` classifies scope errors: only `ENOENT` means `PATH_NOT_FOUND`; preserve other filesystem errors. Caller globs reach rg as `--glob`, so a positive glob overrides ignore rules for what it matches, as in rg and Pi's built-in grep. `scopeArgs` appends `!.git` after the caller's globs, so no glob admits `.git`; Pi's grep has no such exclusion, and this difference is deliberate.

## Regex workers

`regex-worker.ts` owns timeout, cancellation, and cleanup for grep and replace workers; each caller awaits a request before sending another to the same worker. Each worker (`grep-worker.ts` runs `core/search.ts`; `replace-worker.ts` runs `core/replace.ts`) is started through its `.mjs` bootstrap, which loads TypeScript through `jiti`, because workers do not inherit Pi's loader; workers never import the Pi runtime and trust inputs validated at tool entry. `replace-regex.ts` owns the replacement request and sends regex batches to `core/replace.ts`; literal-only batches remain in-process. `config.ts` owns both timeout settings. The host validates exactly-one-result replies with `regex-worker-contract.ts`, using code-specific facts from `report-schema.ts` and each engine's result schema (`core/replace-schema.ts`, `core/search-schema.ts`); that schema check is a reply's only check, and the host trusts the engine's semantics. Bound worker failures only in the receiving tool.

## Reports and rendering

- Give each model-facing rule one home, chosen by what it decides. Choosing a tool, or a parameter of the call being written, belongs in that tool's `description` or the field's description; an obligation spanning several calls belongs in `promptGuidelines`; what to do about one result belongs only in that report's `next` (`src/pi/report-schema.ts`). State a tool's or field's facts once, where they belong. Guidelines never restate a `next`; `NEXT_GUIDELINE`, appended at registration in `src/index.ts`, ranks a report's `next` above them. Word rules as instructions with a concrete trigger and listed exceptions, not as preferences. Include text that applies to one platform only on that platform, decided from `process.platform` where the text is defined.
- Every tool result states its facts in one report. A success report follows the content payload; a failure report is the whole `isError` result. Layers return structured facts and never append sentences or bracket notices; each fact has one owner, so it appears once. Throw sites classify failures as `HashlineError` with a code and the facts its schema requires; `message` describes only the throwing step, a failure beneath that step is `cause`; native diagnostics remain directly in `message`, without a synthetic wrapper, except that a missing path or a target that is not a regular file gets one fixed message in every tool (`PATH_ERROR_MESSAGES`), with resolved paths in `missing`: producers and throw sites state them resolved, and the report layer (`boundFacts` in `report.ts`) spells them once with `serializeAbsolutePath` in success and failure reports alike, as headers spell paths, then cuts each list in `BOUNDED_LISTS` to whole entries within the diagnostic block and counts the omitted entries; `next` is derived from the code and publication (a throw site may only select one of the code's named alternatives). Text shared by success and failure (such as `REREAD`) is defined once in the schema module.
- Send the model a result field only when its value changes the model's next call. Do not send a field that is a function of the call's own arguments, or that the same result already states (a payload header, a row, another field). What only a person can act on (diffs, progress, display-callback failures) goes to the TUI through `details`; revisions, candidate strategy, and timing stay out of results. In review, delete a field when nobody can say what the model does differently for another value of it.
- A success report carries `next` only when the result is incomplete or the model would otherwise misread it. A failure's `next` names a tool or parameter whose values the same report supplies; a code with no such action has no `next`. Order `OUTCOME_NEXT` so that following an earlier rule makes a later one reappear on the following call.

- `report-schema.ts` is the single definition of the result protocol: every report field in output order (each with one owning layer), its schema, audience, and model decision purpose, every error code with its facts schema and recovery (`next.default` plus named alternatives), and the success recovery order (`OUTCOME_NEXT`). `FACT_FIELDS` is the required declaration point; model omission is derived from its audience together with the call fields, so `report.ts` does not maintain a second field set. Checked report types retain their tool or error-code variant; absent fields remain readable as undefined. Types derive from it. Its closed wire schemas validate text-only reports, enforce legal tool names, and require code-specific facts.
- `report.ts` builds reports and owns their one model-facing serialization (`renderReport`: one JSON object, fields in schema order). Result text omits the call's own `tool`/`path` and TUI-only facts, which stay in `details.report`. `reportResult` appends a success report after the tool's payload only when the report states a model-visible fact or the result has no payload. When it appends a block, it records its zero-based position as `details.reportBlockIndex` for the TUI and session replay. After the execution-entry argument check, every tool runs inside `runTool`, which classifies a failure (`describeFailure`, structured `cause`, `next` from code and publication) and returns it as an `isError` result whose `details.report` the TUI renders. This module receives a mutation's failure facts from `mutation-result.ts` and does not depend on the commit layer.
- `reportBlockIndex` is present only when the success builder appends a report block. It belongs to the persisted TUI details format. Model-facing content, script output, and failure details use their own contracts. The [root replay contract](../../AGENTS.md#behavior-contracts) governs persisted format changes. Without a recorded index the success splitter leaves the content intact.
- `SCRIPT_OUTPUT_SCHEMAS` defines the full success facts for each tool. Producers derive their input types from it, so each mutation supplies `publication`, replace supplies `matches`, and grep supplies `matches` and `files`. The success wire schemas allow omitted fields when decoding reports. `reportResult` projects the complete facts into Pi's `structuredContent`, model payload, and report. Visibility flags carry no fact values. Counts already shown by grep's payload and a continuation already known from read's caller limit stay out of report text, its `next`, and `details.report`. The final session Bash text and image content blocks reach the model in order with native formatting, limits and truncation, without a Hashline field-budget pass; the separate report states the command's status. Scripts get `then_run.status` and native structured fields when supplied: `output` (raw stdout/stderr, possibly empty), `truncated`, optional `full_output_path`, `exit_code`, and `wall_time_seconds`. Permission blocks, timeouts, skipped commands, or overrides without a native structured result can have status alone, with diagnostics in content. The TUI retains native command card behavior. Scripts get the read or grep payload as `text`. A delegated image read passes Pi's image object through. A delegated read of a file containing NUL gives `{ text }` with Pi's output and no report facts.
- `render.ts` (`reportLines`) is the one TUI renderer of a report and holds the shared tool renderers. Render inputs admit partial details independently of the current execution result. Success renderers get the checked report and payload from `splitReport`. It strips a trailing text block only when its index equals `details.reportBlockIndex` and its text equals `renderReport` of the checked report. If a hook removes the report or changes its position or text without updating the corresponding details, the split preserves all content blocks and still returns any checked report facts. A hook that replaces a report with identical text at the same index can clear `reportBlockIndex` in its replacement details to mark that block as payload. Failure rendering uses `renderToolError` and `details.report`. The argument boundary throws before file access. A text-only argument rejection decodes from the final content block through `reportOf`. Both decoders check the same wire schema and require the originating call's tool. Only the text decoder fills in an omitted tool. Invalid text-only reports remain raw.
- A collapsed preview that hides rows ends with one marker in the form Pi's built-in cards use. Its expand hint comes from the render context's `keyHint`, because an imported `keyHint` can belong to another copy of Pi that does not see the host's keybindings. On a success card the report's facts follow the marker and stay visible when collapsed. `read` shows nothing when collapsed, as Pi's `read` does. A call line shows its path as Pi's cards do: the home directory as `~` (`shortenHomePath` in `path.ts`), and for `edit` and `replace` a link to the file where the terminal supports links (`formatHeaderPath`). `read` and `write` use Pi's own call renderers, and grep shortens without linking, as Pi's grep does. Pi exports neither path helper, so both are local. A card's body starts on the row under its call line, without the blank row Pi's built-in cards leave there. This difference from Pi is deliberate.
- A collapsed mutation card counts all diff rows for the header and overflow marker. Its preview passes only the visible rows and two rows of lookahead to Pi's `renderDiff`, which emits one row per input row and applies word highlighting only to a single removal followed by a single addition. The lookahead preserves that decision at the cutoff. Expanded cards pass the entire saved diff to Pi.
- `report-cause.ts` transports structured causes without Pi runtime imports, preserving cause chains with cycle protection; reports and worker replies share it. Native failures state the original diagnostic and errno once in `message`, retaining only an actual underlying `Error.cause`.
- To add or change a report field: (1) declare it in `FACT_FIELDS` under its owning layer's group, including its audience and, for model-visible facts, the decision it changes: the concrete call the model makes differently for each value (`decide whether…` and `account for…` name no call); (2) include it in each tool's `SCRIPT_OUTPUT_SCHEMAS` entry, the success TUI fields, or each `ERROR_DEFINITIONS` code that carries it; (3) when it needs recovery, add one `OUTCOME_NEXT` rule or the code's `next`, never a sentence at the producing site; when the recovery depends on the call's arguments, the rule names alternatives and the producing layer selects one (`OutcomeVariant`, passed to `reportResult`), so the text never asks the model to branch; (4) produce it in that one layer, bounded by the call's budget; a list of whole items is instead listed in `BOUNDED_LISTS` with its omitted count, and the report layer bounds it; (5) leave `render.ts` alone unless a card presents the fact another way, and then name it in that card's shown set; (6) check the README passage for the tool. To change an error code, edit `ERROR_DEFINITIONS` and follow the type errors to every throw site and the worker contract.
- `error-text.ts` holds the Pi-layer error forms (cancellation, file changed during read or search). `diagnostic-buffer.ts` bounds stderr and search diagnostics.

## Budgets and config

- `budgets.ts` defines the model-facing byte budgets, and `model-budgets.ts` derives them on each request only from the live selected model's declared capacity, never remaining context; an explicit `read.maxKiB` overrides only the read cap. Preparation shares the provider, and each execution captures its budgets before its asynchronous work; internal helpers require the resolved budget or an explicit byte limit. Model-derived budgets and the `read.maxKiB` range share the `MAX_CONTENT_KIB` ceiling.
- `config.ts` defines the `hashlineEdit` settings as one TypeBox schema, the only definition of their types, ranges, and defaults: shared top-level settings and the `read`, `grep`, and `replace` groups. A project's `.pi/settings.json` field replaces the global one (under `getAgentDir()`) as a whole; each setting is validated on its own and falls back to its default when missing or invalid. A missing or invalid `read.maxKiB` selects automatic model sizing. Tools receive the resolved configuration at registration and keep it for their lifetime; a change requires a reload.

## Action Fusion

`action-fusion.ts` implements `then_run`. After a successful mutation it checks freshness against `publishedRevision`, then runs the command through the session's Bash with `ctx.executeTool("bash", ...)`, honoring overrides and the `tool_call` and `tool_result` hooks. The final session result decides the command's status, `terminate` passes on to the parent result, and a failed command does not roll back published files. Its own per-file queue wraps mutation and command around Pi's `withFileMutationQueue`; the module header explains the nesting. At Bash completion Fusion records `terminate` and each command fact as soon as Pi's result determines it. It reads indexed content into plain blocks once and gives progress subscribers a separate copy from the model payload. `native-bash.ts` takes the script fields from Pi's Bash output schema and shares the native definition with the card renderer. A finite `exit_code` establishes that the command exited even when the structured result is incomplete. Unreadable structured fields or display details are recorded in `progressError`. Model content, the known command outcome and the termination request survive those observer errors. A pre-run cancellation settles without reading output. Fusion progress derives from `ACTION_FUSION_PROGRESS_SCHEMA`. `fusion-card.ts` checks foreign card data, including restored session entries. The decoder verifies the progress schema and indexed content array before handing a result to Pi. Session entries receive a separate structured clone at each endpoint because `appendEntry` dispatches synchronously. Card snapshots copy the JSON representation of the fields Pi's Bash renderer reads: `fullOutputPath` and the `truncation` fields `truncated`, `truncatedBy`, `outputLines`, `totalLines`, and `maxBytes`. Other override details do not enter the card. It renders the separate mutation and command TUI cards (`withMutationStatus`, `registerFusionCards`) and derives a not-run reason from the same facts.

Fusion matches its nested Bash `tool_call` by parent ID inside the dispatch scope. Bash's first execution update fixes the displayed command and snapshots the hook-edited timeout for the countdown and final classification. For a silent override, Fusion reads the fallback timeout only for a final error with an execution duration and no numeric exit code. It checks for cancellation after timeout classification. Fusion reports `timeout` when Pi returns a final error with an execution duration, without a structured numeric exit code, and the final text matches or ends with Pi Bash's diagnostic for the observed timeout. Pi measures execution duration only for calls that ran. A silent override or result hook can change the shared input or final output, so this classification depends on them preserving the timeout and its diagnostic.

Cancellation releases a waiting call's turn without releasing its predecessor. The queue entry stays until its chained tail settles, so nested calls still see an occupied target.

Command cards reuse Pi's public `ToolExecutionComponent`, with the real TUI supplied by a temporary empty widget factory. History may be rebuilt before `session_start`, so retain a deferred component until the UI is bound. Cache each native component by call ID and apply global expansion only when that setting changes, so custom-entry rebuilds preserve mouse expansion. Keep spacing adaptation separate from native mouse handling and retain the built-in Bash presentation; the supported Pi API does not expose another tool's renderer.
