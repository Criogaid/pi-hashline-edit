# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Project rules, behavior contracts, verification policy, and commit/release conventions live in AGENTS.md and apply here as well:

@AGENTS.md

## Test ownership

Claude works on business code only. Never read, write, or edit test files: `*.test.ts`, `*.testing.ts`, `src/integration/`, or test fixtures. This rule overrides the test-related parts of AGENTS.md and of the sections below.

- When a business-code change breaks or needs tests, do not touch them. Instead, output a self-contained prompt for another model to do the test work: what changed in the source, the new signatures and behavior, what to cover, and how to verify.
- Running `npm run format:check`, `npm run typecheck`, and the test commands to report their results is allowed. When a failure comes from a test file, report it and hand it off through the prompt; do not open the test file to diagnose it.

## Commands

TypeScript runs directly through Node's type stripping, so there is no build step. CI uses Node 24 and also tests 22.19.0 and 26, on Linux, macOS, and Windows.

- `npm run format:check` / `npm run format` — Biome, formatting only, scoped to `src/` and `bench/`.
- `npm run typecheck` — `tsc --noEmit` over source and tests.
- `npm test` — run core and tool tests through `src/testing/run-tests.ts` with an isolated Node environment and temporary Pi agent directory.
- Single case: `npm test -- --test-name-pattern "<regex>"`; use the same option with `npm run test:integration`. Direct `node --test` commands bypass the environment isolation.
- `npm run test:integration` — bundled ripgrep, installed-package workers, and files over 100 MiB. `npm run test:all` runs both isolated suites and matches CI and publish.
- `npm run bench`, `node --expose-gc bench/grep-memory.bench.ts` — throughput and grep memory benchmarks.
- `node bench/argument-validation.bench.ts` — argument preparation plus Pi validation, without executing tools.

## Architecture

The extension replaces Pi's built-in `read`, `grep`, `edit`, and `write` tools and adds `replace` plus the optional `forget` tool. `src/index.ts` loads the config once and passes it explicitly to each tool factory, which keeps that snapshot for its lifetime. When `enabled` is false it registers nothing. Otherwise it registers tools from their `make*Override` / `makeReplaceTool` factories and calls `registerForgetTool` only when `forget` is enabled; when `actionFusion` is on, the three mutation tools also receive the Action Fusion executor and are wrapped with `withMutationStatus`.

**`src/core/`: internal pure engine, with no Pi imports and no public API.** It trusts input already filtered by the tool layer and does not re-validate it. `hash.ts` computes position-dependent line checksums (line number + content → `LINE#HASH`). `lines.ts` handles splitting and line-ending detection. `text.ts` does strict UTF-8 decoding. `apply.ts` `applyEdits` validates a whole batch of `Edit` ops (see `types.ts`) against a single snapshot: anchor checks, overlap and conflict detection, and shifted-anchor recovery (`AnchorRecovery`: local `shiftRadius` search, then full file). It returns new text or structured failures and never touches the filesystem. `replace.ts` is replace's engine: literal and JavaScript-regex matching on the LF view, separator restoration, and overlap rejection. `search.ts` evaluates native JavaScript queries on the LF view and returns bounded physical rows; `search-schema.ts` defines its result. `errors.ts` holds the classified `HashlineError`, typed by code so its facts and `next` alternative must match the code's schema, and errno classification. Core's report references are type-only and erased at runtime. `replace-schema.ts` defines the tool's replacement schema and the engine's derived rule type. `ranges.ts` provides overlap detection for both engines and range merging for grep and failure neighborhoods.

**`src/pi/`: Pi integration.**
- Tool files (`read-tool.ts`, `grep-tool.ts`, `edit-tool.ts`, `replace-tool.ts`, `write-tool.ts`) define TypeBox schemas. Input is filtered once at the top of the funnel: each tool's `prepareArguments` comes from `argument-validation.ts` (described below), then Pi validates against the schema again, and only then calls `execute`. Caller arguments are never rewritten. Each tool supplies only the semantic checks the schema cannot express or name precisely: edit rejects empty bodies, body lines that cannot be written as UTF-8, line numbers beyond the safe-integer range, and anchors of another hash length; replace rejects unwritable replacement text and compiles regex rules; write rejects unwritable content. `execute` trusts its input and does not re-validate. Tests that probe invalid input go through `callTool` in `tool-call.testing.ts`, which follows the same order. Shared integer rules live in `schema.ts`; error codes and every report field live in `report-schema.ts`.
- `mutation-runner.ts` owns the call sequence shared by `edit`/`replace`/`write` after Pi has validated the arguments: separating `then_run`, path resolution, `withFileMutationQueue`, and the hand-off to Action Fusion or plain finalization. Each tool's `run` returns a typed `MutationOutcome` (commit facts, details, outcome facts), and only `finalizeMutation` turns it into a result; nothing downstream reads publication or revisions back from result details. `runTextMutation` owns the read-modify-write for `edit`/`replace`, so each tool supplies only a `TextChange` (new text, outcome facts).
- grep is split into `grep-tool` (schema and execution order), `grep-scope` (paths and glob admission), `grep-plan` (engine selection and compile checks), `grep-search` (`SearchRequest`, `GrepBackend`, rg JSONL events, per-file revisions), `grep-output` (payload rows, file-header format and its parser, and grep's report facts), and `grep-render` (TUI rows). `rg-process.ts` is the ripgrep process layer: spawning, bounded reading, matcher arguments, and the regex compile probe. `GrepBackend.search` takes a structured request, so scope flags are produced only by `scopeArgs` and never parsed back. Grep and replace share JavaScript regex syntax: `rg-regex.ts` parses grep patterns with regexpp (V8 has already accepted them in `prepareArguments`) and translates each into an `RgMatcher` with JavaScript semantics on the LF view (explicit character sets and case folding, CRLF-aware breaks and anchors, PCRE2 for lookaround, backreferences, and JavaScript line-boundary assertions) and decides smart case on the parsed pattern. `grep-plan.ts` selects `grep-javascript.ts` when translation or compilation cannot preserve the query, including Unicode and sticky modes. This adapter uses rg file discovery, guarded reads, and the existing snapshot/output pipeline with native matching in `core/search.ts`. V8 validates pattern syntax and flags at entry; case overrides resolve once into `GrepQuery.flags`. README defines resource limits and physical-line reporting.
- Logical text view: every tool hashes and matches on a CRLF→LF view. Mutations map offsets back to the original bytes so untouched separators, BOM, and final-newline state survive. Grep's rg path runs bundled `@vscode/ripgrep` on the original files with `--crlf`, relying on the translation for LF-view semantics; `text-stream.ts` and `rg-line-ranges.ts` map its reports to logical lines, and each matched file is read once for NUL, UTF-8 validity, and its revision.
- `regex-worker.ts` owns serialized requests, timeout, cancellation, and cleanup for grep and replace workers. Their `.mjs` bootstraps load TypeScript through `jiti`, because workers do not inherit Pi's loader. `replace-regex.ts` sends regex batches to `core/replace.ts`; literal-only batches remain in-process. `grep-javascript.ts` sends one file per request to `core/search.ts`. `config.ts` owns both timeout settings. Workers trust inputs validated at tool entry. The host validates exactly-one-result replies with `regex-worker-contract.ts`, using result schemas and code-specific facts from `report-schema.ts`; `replace-worker-contract.ts` owns replacement request/result shapes. `report-cause.ts` transports structured causes without Pi runtime imports.
- `file-commit.ts` is the only publication path. It does SHA-256 revisions (`byteRevision`/`fileRevision`), no-op detection, a temp file in a sibling dir, then `link` (create) or `rename` (overwrite). It also handles symlinks and hard links, preserves file modes, and syncs the directory on POSIX. It throws `FileMutationError` with a `stage` and a `NOT_PUBLISHED`/`PUBLISHED`/`UNKNOWN` publication status; a failed step is the `message`, its underlying error the `cause`. `edit`/`replace` pass the revision of the bytes they read as `expectedRevision`. It also owns freshness: `commitFreshness` from the commit result and `observeFreshness` for Fusion's later observations.
- `mutation-result.ts` builds diff details and defines `MutationOutcome` and `finalizeMutation`, which returns one mutation report from commit, tool, freshness, and command facts. Successful mutations return no anchor payload. `failure-context.ts` turns anchor failures into a `HashlineError` with bounded facts (`failures`, `matched`, `candidateNeighborhoods`); `anchor-format.ts` owns the `LINE#HASH` syntax, its schema pattern, and row parsing.
- `argument-validation.ts` owns every tool's `prepareArguments` hook, issue collection, bounded diagnostic output, and Pi schema validation adapter. Tools report semantic field issues through its callback; they do not throw during collection. Successful schema conversion informs those checks without changing caller arguments. Pi then performs its mandatory validation again. Top-level tool fields have independent schemas; failure diagnosis derives field schemas with TypeBox and keeps Pi's coercion and per-field error limits. When a schema reason does not say how to correct the value, its `fix` comes from the declaration: a missing or pattern-mismatched field gets its description (each choice's value and description), and a forbidden field gets the selected shape's accepted fields after the meaning of the operation that selected it. File-dependent checks stay in execution.
- Model-facing text follows the ownership rule in AGENTS.md. Tool and parameter choices live in each tool's `description` and field descriptions beside its schema, so each mutation tool's description names its alternative (edit ↔ replace ↔ write); obligations spanning several calls live in `promptGuidelines`; recovery for one result lives only in the report's `next`. `src/index.ts` registers read, grep, and the mutation tools through one helper that appends `NEXT_GUIDELINE` from `report-schema.ts`, ranking `next` above the guidelines; Pi prints the shared guideline once. With Action Fusion, `withThenRunDescription` appends the one then_run selection sentence, as `withThenRunSchema` adds the field; the field's `command` description carries the Windows path note only when `process.platform` is `win32`. `budgets.ts` derives model-facing byte budgets from the selected model's declared `contextWindow`, with bounded defaults for unknown limits. `model-budgets.ts` caches one immutable snapshot per extension, calculated lazily and replaced when selection or capacity changes; preparation shares its provider and executions capture it before asynchronous work. Remaining context is never queried. An explicit `read.maxKiB` in the settings schema overrides only the read cap; model-derived content budgets share the same `MAX_CONTENT_KIB` ceiling. `error-text.ts` holds the Pi-layer error forms (cancellation, file changed during read or search). `report-schema.ts` is the single definition of the result protocol: every report field in output order (each with one owning layer), every error code with its facts schema and recovery (`next.default` plus named alternatives), and the success recovery order (`OUTCOME_NEXT`). Types derive from it. `report.ts` builds reports and owns their one model-facing serialization (`renderReport`: one JSON object, fields in schema order): `reportResult` appends a success report after the tool's payload, and every tool's `execute` runs inside `runTool`, which classifies a failure (`describeFailure`, structured `cause`, `next` from code and publication) and returns it as an `isError` result whose `details.report` the TUI renders. Argument errors from `argument-error.ts` are reports too; Pi raises them before execution, so the TUI decodes them with `decodeReport`. `render.ts` (`reportLines`) is the one TUI renderer of a report. Text reports contain only facts; closed wire schemas enforce legal tool names and required code facts. Text-only argument rejections and forget tags decode from the final content block. Native failures state the original diagnostic and errno once in `message`, retaining only an actual underlying `Error.cause`. Failure rendering uses `details.report`, with final-block decoding for Pi's text-only argument rejections. Invalid text-only reports remain raw. `report-cause.ts` preserves cause chains and aggregate branches with cycle and repeated-reference protection; reports and worker replies share it.
- `action-fusion.ts` implements `then_run`. After a successful mutation it checks freshness against `publishedRevision`, then calls the session Bash tool through `ctx.executeTool("bash", ...)`, including overrides and tool hooks. The file result and the command result stay separate, and a failed command never rolls back the file. Its own per-file queue wraps mutation and command around Pi's `withFileMutationQueue`; the module header explains the nesting. Fusion states only the command (`then_run` status and output, `terminate`); freshness and publication come from the mutation report. Fusion progress derives from `ACTION_FUSION_PROGRESS_SCHEMA`; `fusion-card.ts` validates saved command cards against its closed projection before restoring them. It renders the separate mutation and command TUI cards (`withMutationStatus`, `registerFusionCards`) and derives a not-run reason from the same facts; `render.ts` holds the shared tool renderers.
- `forget-tool.ts` implements `forget`, disabled by default through the `forget` setting. When enabled, read and grep tag large results with `withResultTag`, which adds the forget-owned `resultId` fact to their report; a `context` handler records the tagged results of the previous response, `forget` forgets the named ones among them and reports the rest in `notForgettable` (failing with `NOT_FORGETTABLE` only when none qualifies), since no later response can forget them, and its `turn_end` handler uses Pi's `context_edit` to replace each result's entire content with a forgotten receipt. It does not parse or classify the content; the original tool call and facts saved in `note` remain. Older results are never edited, so the next request changes only from the earliest replaced result on: later results of that batch, the response that asked, and its tool results. Tagged results also carry a display-only `forgetReceipt` in details (`readReceipt`/`grepReceipt`), which `forget` copies into its own details for the TUI card; nothing of it reaches the model.
- `config.ts` defines the `hashlineEdit` settings as one TypeBox schema (types, bounds, defaults): top-level `enabled`, `actionFusion`, `forget`, `hashLen`, `shiftRadius` control shared behavior; the `read`, `grep`, and `replace` groups hold tool-specific settings. Invalid leaves fall back to their defaults individually; missing or invalid optional `read.maxKiB` selects automatic model sizing.

**Tests:** `*.test.ts` files sit next to their sources. `registration.test.ts` covers configuration wiring; `read.test.ts` covers reads; `execute.test.ts` covers edits and shared mutation workflows. `failure-path.test.ts` and `result-safety.test.ts` cover publication failures and result safety. `argument-validation.test.ts` covers combined argument failures through tool entry points. `forget.test.ts` drives forgetting and argument rejection through real Pi sessions using the shared local-model fixture in `forget.testing.ts`; `src/integration/forget-grep.test.ts` uses the same fixture with real ripgrep. `tool-call.testing.ts` provides production-order tool calls and native Pi tool contexts with test-scoped cleanup. Tests requiring real ripgrep, large files, or platform-specific behavior belong in `src/integration/`.

`src/testing/session.testing.ts` owns Pi session initialization, local model response streams, credential and resource isolation, and cleanup. Tool contexts, forget sessions, and Fusion sessions share it; their registration and business assertions stay with the feature.

`src/testing/process.testing.ts` owns clean child-process environments; `installation.testing.ts` creates source or npm archive installations with only locked production dependencies; `extension-loader.testing.ts` loads them through Pi's jiti and virtual modules. `src/integration/npm-package.test.ts` covers the archived package's registered tools, worker, command dispatch, and context editing.

README.md is the user-facing contract: tool parameters, output budgets, recovery semantics, and publication states. Keep it in sync with behavior changes.
